The repo can hold the facts. Now: how you askM1

The problem

  • An AI agent usually writes a likely answer — instead of saying it does not know.
  • This module shows how to make it stop and ask instead.

What you will learn

  • A clear shape for every request.
  • How to check where an answer came from.
  • How to prove one prompt is better than another.
Watch for: a model that is never unsure is guessing.

Words used in this moduleM1

AI and agent words

  • Agent — Copilot in agent mode. It reads files, edits code and runs commands.
  • Turn — one message from you plus one reply.
  • Context window — everything the agent can see in this chat.
  • Hallucination — a made-up answer that looks real.
  • Grounding — making the agent show where a fact came from.

Course and Global Bank words

  • ADR — a short file that records one design decision (docs/adr/).
  • Acceptance criteria — the checklist in a ticket that defines “done”.
  • Posting — one money movement between accounts.
  • Reversal — undoing a posting. Nothing is deleted.
  • Ledger entry — one saved line of account history. Never edited.

Six parts of a good request — and what goes wrong without each1

The same ticket, asked twice — GB-1511

What most people type
THE ORDINARY REQUESTAdd a reversal endpoint for postings.

What the agent must now guess

  • Should a reversal delete the posting, change it, or add a new one? (The ticket already answers this.)
  • Which files to change.
  • When it is finished, and what to do if unsure.
You cannot see these guesses in the code it writes.
The same request, with the six parts
THE ENGINEERED REQUESTGOAL Add POST /api/v1/postings/{id}/reversal. CONSTRAINTS - Follow docs/conventions.md and .github/instructions/api.instructions.md - A reversal changes the posting's status. It never deletes it. (docs/glossary.md) - Do not store balances. They are calculated. INPUTS - posting/service/PostingService.java - posting/domain/Posting.java - GB-151, all six acceptance criteria - Copy the style of posting/api/PostingController.java OUTPUT CONTRACT - Controller + service + slice tests - No new dependencies - Errors in ProblemDetail format DONE - mvn test passes; the new test fails on the old code - A second reversal is rejected STOP - If no file says how to reverse, stop and ask. Do not choose. - Do not change existing ledger entries.

Stop conditions — tell the agent when to stop and ask1

Make them checkable

  • “Ask if unsure” is too vague.
  • “Ask if no ADR covers this” is clear.

Where to find them

  • Look at the fix-up prompts you type in Lab 1. Each one is a missing stop condition.
Remember: the agent will not tell you what it did not know. A stop condition makes it tell you.

Output contracts — make the answer checkable1

the shape you ask for — GB-151# Reply with this object and nothing else. { "ticket": "GB-151", "files_changed": [ "PostingService.java", "PostingController.java", "PostingServiceSliceTest.java" ], "rules_used": [ { "rule": "two ledger entries", "source": ".github/copilot-instructions.md" } ], "tests_added": [ "PostingServiceSliceTest#reversal" ], "unresolved": [ "anything you had to guess" ] }

Why a shape beats a paragraph

  • A person can read it in ten seconds.
  • A script can check it. Prose cannot.
  • files_changed shows scope drift at once.
  • unresolved gives the agent a place to admit a guess.
Asking for JSON is not enough. Say the reply is the object and nothing else.

Four prompting patterns — and how to use them with an agent1

Mode decides how much Copilot may change2

Instruction file, skill file, prompt — what goes where2

Common mistakes

  • Steps in the instruction file: it grows too long, and people stop reading it.
  • Facts in the prompt: you type them again every time.

Why a file?

  • Steps in one person’s head leave when that person leaves.
  • In the repo, anyone can review and improve them.

The instruction file — facts, read every time2

.github/copilot-instructions.md — shortened## Read these before proposing a change - docs/architecture.md, docs/conventions.md - docs/glossary.md — our nouns are not the obvious meanings - docs/adr/ — check for an existing ADR ## Non-negotiables - Money is a long of minor units. Never double, float or BigDecimal. See ADR-003. - Every posting writes exactly two LedgerEntry rows, one DEBIT and one CREDIT. - Balances are derived, never stored. - Constructor injection only. No Lombok (ADR-005). - Cross-currency postings are rejected. ## When you are unsure - Say so and ask. Do not invent an id, a currency code or a limit. - Quote the file you are relying on.

What belongs in it

  • Facts only. No steps.
  • What a new joiner would get wrong.
  • Where to look before proposing a change.
If it runs past one screen, you have started writing steps.
In Lab 3 you write this file for your own team.

A skill file — the reusable half of a request2

.github/skills/account-change/SKILL.md — shortened--- name: account-change description: Implement a change to posting or balance behaviour in global-bank-account metadata: version: "3" owner: payments-platform --- # Before you write anything 1. Read docs/adr/README.md and open any ADR that the ticket touches. 2. Quote the rule you are relying on, and the file it came from. # Rules See .github/copilot-instructions.md. # Facts live there, and in # .github/instructions/. Do not repeat them. # Output contract - Service method + controller + slice tests. - Errors in ProblemDetail format. - No new dependencies without an ADR. # Done: mvn test green; new test fails on old code. # Stop and ask — do not choose - The ticket can be read two ways. - A design choice with no ADR. - Any change to an existing ledger entry.

The header

  • name — must match the folder name.
  • description — Copilot reads this to decide when to use the skill. Be specific.
  • version, owner — so someone keeps it up to date.

The body

  • The six parts from slide 4, minus goal and inputs. Those come with each ticket.
  • “Stop and ask” lists mistakes the team already made once.
Notice: no facts here. It points at the instruction file instead.

What makes a skill file useful to the whole team2

In Copilot — prompt files and #codebase2

.github/prompts/gb-change.prompt.md--- description: Start a Global Bank change from a ticket agent: agent argument-hint: ticket=GB-nnn goal=... --- Follow the account-change skill. Ticket: ${input:ticket} Goal: ${input:goal} Inputs: the files the ticket names, and the file whose style it says to copy. If you cannot name them, search #codebase, list what you found, and wait for my OK. # in chat: # /gb-change ticket=GB-151 goal="reversal"

Prompt file or skill?

  • Prompt file — you run it by typing /gb-change. It only fills in the ticket and goal.
  • Skill — Copilot loads it by itself when the task matches its description. The steps live here.

#codebase (older: @workspace)

  • It searches the whole repo for you.
  • Use it once to find the right files. Then name them in your prompt.
Search once to find the files. After that, name them.

Four grounding rules — make the agent show its source3

What grounding means

  • The agent must point to where a fact came from — a file in this repo.

Why it works

  • A guess becomes easy to spot.

Where to put them

  • In the skill file, once. Not in every prompt.
A rule with no clear trigger and no check does nothing.

The same question — with and without grounding3

Without grounding — sounds right
“HOW DO I STOP THE SAME PAYMENT BEING POSTED TWICE?”Ask the caller to send a unique Idempotency-Key header. Save it with the posting. If the same key comes again, return the first posting. This is the usual way for payment APIs.

The problem

  • Good advice in general. Wrong for this repo.
  • No source, so you must check the whole repo yourself.
With grounding — source, code, and the gap
SAME QUESTION, GROUNDING RULES IN THE SKILL FILEIn this repo, duplicates are found by clientReference + valueDate. Source: docs/glossary.md line 14, and docs/adr/ADR-007. A header key was rejected: two large upstream systems do not send it when they retry. Existing code: PostingRepository has findByClientReference(String) only. ADR-007 is accepted, not built yet. Not found: whether a reversed posting still counts as a duplicate. ADR-007 does not say. Stopping to ask.

Four common agent failures — and how to catch each4

How strong each fix is4

The pattern

  • Do not write prompt rules for what the build already catches.
  • Spend effort on failures only a person who knows the system can spot.
In Module 3 you accept a bad suggestion on purpose, and catch it with a test.

Tests written to pass — when a green tick proves nothing4

Why it happens

  • You ask for the code and its tests together.
  • Both come from the same understanding of the ticket.
  • If that understanding is wrong, both are wrong — and the tests still pass.

Three warning signs

  • It only checks that no error was thrown.
  • It only checks that a mock was called.
  • It repeats the code’s logic instead of checking the result.

Start a new chat — and re-brief in one paragraph5

new chat — all you need to typeFollow the account-change skill. Ticket: GB-151 — reverse a posting. Decided: a reversal changes the status. It never deletes. (docs/glossary.md) Rejected: a stored balance column. Do not suggest it again. Done: service method + its test, passing. Next: the controller and its slice test. #file:posting/service/PostingService.java #file:posting/api/PostingController.java # Rules and ADRs are already in the repo # (the instruction file), so not repeated here.

Why long chats go wrong

  • The agent re-reads the whole chat on every turn. You use more tokens on every turn.
  • Old mistakes and rejected ideas still affect its answers.

Start a new chat when

  • The ticket is done.
  • It suggests something you already rejected.
  • You cannot remember what is in the chat.
In the new chat, write only what is not in the repo: decisions, rejections, progress.

Four signs it is time for a new chat5

Test your prompt on three real tickets6

Why

  • “My prompt is better” is an opinion. A pass rate is a fact.

The trap

  • Picking only tickets your new prompt handles well. Then the test can only agree with you.
Three tickets show a direction, not a trend. Read the two diffs as well as the score.

What to take into Module 2M1

Do this on every request

  • Use the six parts. Never skip stop conditions.
  • Ask for the source of every rule.
  • Typed it twice? Put it in a skill file.
  • Measure with a pass rate, not a feeling.
Your prompts get shorter. The repo and the skill file carry the rest.
