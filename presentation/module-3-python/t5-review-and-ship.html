A Python PR checklist

What you now look for, in order

Correctness — the Python traps

  • Mutable defaults — =[], ={}, =None in a dataclass list field
  • Truthiness hiding a real 0 or ""; is used for values
  • Blocking I/O in async def; sequential awaits that should be gathered
  • Swallowed failures — bare except, except Exception returning a normal result
  • Unbounded input — a limit, size or page with no upper bound

Design — the house rules

  • Domain errors raised inside, translated only at the edge
  • pydantic v2 only; dataclass for domain, model for wire
  • No module-level state; dependencies via Depends
  • logger with %-args, never print; logger.exception for errors
  • HTML through templates, never f-strings; user input never in a hostname, path or SQL
  • Tests unchanged, or changed with a reason a human wrote
Every item here was on a Read the PR slide today. Put this list in .github/copilot-instructions.md so the agent reads it too — then review anyway.

Worth copying into your team's review guide. The left column is what tests sometimes catch; the right column is what usually only a reviewer catches.

When to reject AI-written code

Green tests are necessary. They are not the decision.

Reject outright

  • A test was edited or deleted to pass
  • An error path now returns success
  • A dependency or config change nobody asked for
  • You cannot explain a line of it

Send it back

  • The description claims a benefit the diff does not deliver ("faster", "simpler")
  • More files changed than the task needs
  • Deprecated API that still runs (pydantic v1)
  • No test for the new behaviour

Merge

  • Small, one concern, matches the spec
  • Every finding you raised is now a test
  • You would sign your name to it
  • You could maintain it without the agent
The real-world parallelAn AI suggestion is a pull request from a very fast, very confident colleague who never ran it in production. You would not skip the review for that colleague. Do not skip it here.

"You cannot explain a line of it" is why the module starts with tutor mode: reading Python fluently is what makes that bar reachable.

Git hygiene

Make every change easy to review, and easy to undo

The loop, with an agent in it

git switch -c fix/ask-failure-contract   # one concern per branch
git add -A && git commit -m "before agent"  # a checkpoint you can return to
# ... agent edits, tests run ...
git diff                                   # read it all, before staging
git add -p                                 # stage hunk by hunk: you choose
python score.py                            # green, or it does not commit
git commit -m "Return 503 when an /ask source fails,
instead of an empty 200"                   # the why, not the what
git push -u origin HEAD                    # then open the PR

Python-specific hygiene

  • .venv/, __pycache__/, *.egg-info/ in .gitignore — never committed
  • No secrets in code or .env in git. Read from environment variables
  • Pin what you depend on in pyproject.toml; a new dependency is its own reviewed change
  • Formatting is not a review topic — a formatter (ruff, black) in CI ends the debate
  • Revert beats repair when an agent's change went sideways: git restore . and re-prompt

git add -p is the most useful habit when an agent has touched several files: it forces a decision hunk by hunk.
